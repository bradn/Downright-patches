# Git workflow for this checkout

This folder is a git repository holding upstream Downright plus two local
layers stacked on top. This page says how to build each layer, change one,
and pull in upstream releases.

## Layout

```
main          upstream Downright, untouched (tracks upstream/main)
└ width-patch  measure-cap patch, Quick Look line width, install.sh fix,
               this guide, Scripts/sync-upstream.sh
  └ ios-port   shared engine for iOS, UIKit reading view, iOS app
```

- `upstream` is the only remote: <https://github.com/ezzy1630/Downright>.
  It is someone else's repository. Never push to it.
- `width-patch` is what the Mac app in `/Applications` should be built from.
  See `WIDTH-PATCH-HANDOFF.md` for what it changes.
- `ios-port` also changes shared Mac code (platform layer, presentation maps,
  decoration replay). See `IOS-PORT-PLAN.md`.

See what a layer changes:

```bash
git diff main width-patch
```

```bash
git diff width-patch ios-port
```

## Before switching branches

Commit or stash first; `git status --short --untracked-files=no` should print
nothing. Untracked files follow you across branches. On `width-patch`,
`iOSApp/Generated/` shows as untracked; that is generated by the iOS build and
is only ignored on `ios-port`.

## Build and install the Mac app

Requires macOS 14+, Xcode, Swift 6 and `xcodegen` (Homebrew).

1. Pick the layer. For the everyday Mac app, use the width patch alone:

   ```bash
   git checkout width-patch
   ```

2. Run the source gate. It must pass with a non-zero test count:

   ```bash
   Scripts/check.sh
   ```

3. Build the production-shaped app (includes Quick Look and thumbnails):

   ```bash
   DOWNRIGHT_HOST_BUNDLE_IDENTIFIER=com.ezzy.downright Scripts/bundle-xcode-app.sh
   ```

4. Quit Downright, then install that exact build:

   ```bash
   APP_SOURCE=.build-xcode/Build/Products/Release/Downright.app Scripts/install.sh
   ```

5. Go back to the iOS work when done:

   ```bash
   git checkout ios-port
   ```

Building from `ios-port` instead also works; it gives a Mac app that includes
the shared-code changes from the iOS work.

## Build and test the iOS side

On `ios-port`, run both gates. `check-ios.sh` does not replace `check.sh`.

```bash
Scripts/check.sh
```

```bash
Scripts/check-ios.sh
```

`check-ios.sh` builds the engine for iOS devices, runs the shared tests on a
simulator, then generates and tests the app in `iOSApp/`. To work on the app
in Xcode:

```bash
cd iOSApp && xcodegen generate && open DownrightIOS.xcodeproj
```

**Running on a device** needs your own Apple team ID and bundle prefix. They
live in `iOSApp/Signing.local.xcconfig`, which git ignores, so they are never
committed or exported; `iOSApp/Signing.xcconfig` holds the placeholders
(`com.example`, no team) and explains why the local file is pulled in with an
optional `#include?`. Create the local file once:

```bash
printf 'DOWNRIGHT_BUNDLE_PREFIX = com.yourname\nDEVELOPMENT_TEAM = ABCDE12345\n' > iOSApp/Signing.local.xcconfig
```

Your team ID is in Xcode › Settings › Accounts. Then run `xcodegen generate`
again and pick your device in Xcode. The simulator and `check-ios.sh` need
no local file.

The iOS app is not a release surface; nothing in `Docs/RELEASE.md` covers it.

## Changing a layer

Put each change in the lowest layer it belongs to.

- **Width or other Mac-only fix:** commit it on `width-patch`, then carry it
  up into the iOS branch:

  ```bash
  git checkout width-patch
  ```

  (edit, run `Scripts/check.sh`, commit)

  ```bash
  git rebase width-patch ios-port
  ```

- **iOS work:** commit on `ios-port`. If it touches `MarkdownCore` or the
  shared (non-`View/`) part of `MarkdownRender`, run both gates.

## Updating from upstream

Run this whenever upstream releases, or just to check. It is safe to run any
time; it never pushes.

```bash
Scripts/sync-upstream.sh
```

It refuses to start with uncommitted changes, fetches `upstream`, moves
`main`, rebases `ios-port` onto the new upstream with `--update-refs` (so
`width-patch` moves in the same pass), then runs `Scripts/check.sh` on
`width-patch` and both checks on `ios-port`. It stops at the first problem,
prints the commands that put every branch back, and returns you to the branch
you started on. Logs go to `.build-sync/`.

- If upstream hasn't moved, it says so and skips the checks. Use
  `--check` to run them anyway, or `--skip-checks` to update without them.
- **On a conflict** it stops mid-rebase. Fix the files git lists, `git add`
  them, `git rebase --continue` until it finishes, then run
  `Scripts/sync-upstream.sh --check`. To back out instead: `git rebase --abort`.
- Git remembers each conflict fix (`rerere` is on for this repository). When
  every conflict in a step matches one you fixed before, the script reuses the
  fix, says which files, and carries on; the checks then verify the result. It
  stops only on a conflict it hasn't seen. (`rerere` is a per-repository
  setting: `git config rerere.enabled true` and
  `git config rerere.autoUpdate true` in a fresh clone.)
- Commits that upstream already contains are dropped automatically. The script
  says when `width-patch` shrinks or becomes empty.

Most conflicts will be in the iOS layer: it edits many upstream files, mostly
to mark Mac-only code. Updating soon after each release keeps them small.

### By hand

The script does these steps:

```bash
git fetch upstream
```

```bash
git checkout ios-port && git branch -f main upstream/main
```

```bash
git rebase --update-refs upstream/main
```

Then check each layer on its own. Build failures here are the usual sign of a
bad conflict resolution:

```bash
git checkout width-patch && Scripts/check.sh
```

```bash
git checkout ios-port && Scripts/check.sh && Scripts/check-ios.sh
```

### When upstream ships one of these features

- **Width:** drop only the width commit ("Raise the reading-measure cap"),
  not the branch: `width-patch` also carries this guide and the sync script.
  If upstream's version is identical, the rebase drops it by itself. If the
  rebase stops on that commit with conflicts, `git rebase --skip` drops it and
  carries on.
- **iOS:** compare their approach with `ios-port` before rebasing. Keep what
  they don't cover and drop the rest.

## Publishing

This checkout is the development workspace; it is never pushed. What is
published is the patch repository (`Downright-patches`, next to this
checkout), which holds only this fork's own work: new files, and patches
for the upstream files it changes. Upstream Downright is a pinned submodule
there.

After committing here, and after any upstream sync, regenerate and check it:

```bash
../Downright-patches/Scripts/export.sh "$PWD"
```

```bash
../Downright-patches/Scripts/verify.sh --against "$PWD"
```

`export.sh` reads the branch tips only, so uncommitted work is never
exported. `verify.sh --against` fails if the export is stale, or if either
assembled layer differs from `width-patch` or `ios-port`; add `--checks` to
run every test gate in the assembled trees as well.

## Undoing a mistake

Every earlier position of a branch is kept for a while:

```bash
git reflog show ios-port
```

Reset a branch to one of those entries with `git reset --hard <entry>` while
it is checked out. That discards uncommitted changes, so check
`git status --short` first.

## Housekeeping

- Build folders (`.build-*`) are ignored by git and can be deleted at any
  time; the scripts recreate them. They are the first thing to clear when the
  disk is full.
- Commits in this repository are authored with a repository-only identity
  (`git config user.name` / `user.email`); the global git config is unset.
